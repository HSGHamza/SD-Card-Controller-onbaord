# Zybo Z7-10: RV32I Core ↔ SD Card via ARM Mailbox Bridge

A fully synthesizable Verilog system that connects a custom **RV32I soft-core** to the Zybo Z7-10's **onboard microSD card slot** via a shared **AXI Mailbox** in PL, with the **ARM Cortex-A9** acting as a transparent SD card server.

---

## Architecture Overview

```
┌─────────────────────────────────────────────────────────────┐
│                    ZYNQ XC7Z010                              │
│                                                              │
│  ┌─────────────────────────┐    ┌────────────────────────┐  │
│  │  PL (FPGA Fabric)       │    │  PS (ARM Cortex-A9)    │  │
│  │                         │    │                         │  │
│  │  ┌──────────────────┐   │    │  sd_mailbox_server.c   │  │
│  │  │   RV32I Core     │   │    │  (auto-boot from QSPI) │  │
│  │  │   (Datapath.v)   │   │    │           │            │  │
│  │  └────────┬─────────┘   │    │           │ AXI4-Lite  │  │
│  │           │ direct bus  │    │           │            │  │
│  │  ┌────────▼─────────┐   │    │  ┌────────▼────────┐  │  │
│  │  │  AXI Dual-Port   │◄──┼────┼─►│   AXI Dual-Port │  │  │
│  │  │    Mailbox       │   │    │  │     Mailbox      │  │  │
│  │  │ (axi_dual_sd_    │   │    │  │ (same RTL block) │  │  │
│  │  │  mailbox.v)      │   │    │  └─────────────────-┘  │  │
│  │  └──────────────────┘   │    │                         │  │
│  │                         │    │  ┌─────────────────────┐│  │
│  └─────────────────────────┘    │  │  PS SDIO0 (MIO 40-45)││  │
│                                 │  │  → microSD J1 slot   ││  │
│                                 │  └─────────────────────-┘│  │
│                                 └────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**Why ARM as helper?** The Zybo Z7-10's microSD slot (J1) is wired directly to Zynq PS MIO pins 40–45. **PL cannot access it directly** — only the ARM PS can. The ARM runs our `sd_mailbox_server` which polls the shared mailbox and services SD read/write requests transparently.

## Mailbox Register Map

The ARM and RV32 share a register file at base address **`0x43C0_0000`**:

| Offset | Register      | Description                                      |
|--------|--------------|--------------------------------------------------|
| `0x000` | `COMMAND`   | `0x01`=READ, `0x02`=WRITE                        |
| `0x004` | `ADDRESS`   | SD Logical Block Address (LBA)                   |
| `0x008` | `CONTROL`   | Bit 0: REQ (RV32 sets this to trigger ARM)       |
| `0x00C` | `STATUS`    | `0`=IDLE, `1`=BUSY, `2`=DONE, `3`=ERROR         |
| `0x010` | `ERROR`     | Error code from last operation                   |
| `0x014` | `SECTOR_SIZE` | Hardware reports 512 (read-only)               |
| `0x018` | `SIGNATURE` | `0x53444D42` = "SDMB" (sanity check)            |
| `0x020` | `DATA[0]`   | 512-byte data buffer (128 words × 4 bytes)       |
| `0x21C` | `DATA[127]` | Last word of data buffer                         |

**Handshake sequence:**
1. RV32 writes `COMMAND` = 1 (READ), `ADDRESS` = LBA
2. RV32 writes `CONTROL` = 1 (REQ bit) → hardware auto-sets `STATUS` = BUSY
3. ARM detects REQ, reads SD card, fills DATA buffer, sets `STATUS` = DONE (2)
4. RV32 polls `STATUS` until 2, then reads `DATA[0..127]`

## Step-by-Step Build Guide

### Prerequisites

| Tool | Used for | Install |
|------|----------|---------|
| `Vivado 2022.x+` | Bitstream + BD synthesis | Xilinx download |
| `arm-none-eabi-gcc` | ARM firmware | `sudo apt install gcc-arm-none-eabi` |
| `bootgen` | Package BOOT.BIN | Ships with Vivado (`<vivado>/bin/bootgen`) |
| `program_flash` | QSPI programming | Ships with Vivado (`<vivado>/bin/program_flash`) |
| `xsct` *(one-time)* | Build FSBL | Ships with Vitis |

> **Note:** After the one-time FSBL build, you **never need Vitis again**. All subsequent builds are Vivado + `arm-none-eabi-gcc` only.

---

### Step 1: Generate Bitstream (Vivado, ~30-60 min)

```bash
cd SD-Controller-onboard
vivado -mode batch -source scripts/build_zybo_project.tcl
```

**Output:** `zybo_rv32i_sd.bit`, `zybo_rv32i_sd.xsa`

---

### Step 2: Build FSBL — ONE TIME ONLY

```bash
# Option A: Using XSCT (headless Vitis CLI)
xsct scripts/build_fsbl.tcl
# Output: fsbl/fsbl.elf

# Option B: Use prebuilt FSBL from Digilent (no Vitis at all!)
# Download the Zybo Z7-10 base design BOOT.BIN from:
# https://github.com/Digilent/Zybo-Z7/releases
# Extract FSBL:
# bootgen -read BOOT.BIN -arch zynq -dump fsbl
# mkdir -p fsbl && mv fsbl.elf fsbl/
```

> After this step, **commit `fsbl/fsbl.elf` to git**. You will never need to rebuild it.

---

### Step 3: Compile ARM Firmware (arm-none-eabi-gcc, ~5 sec)

```bash
# Install toolchain (if not already installed)
sudo apt install gcc-arm-none-eabi

# Compile
./scripts/build_arm_firmware.sh
```

**Output:** `arm_firmware/build/sd_mailbox_server.elf`

The script uses our hand-written BSP in `arm_firmware/bsp/` — **no Xilinx libraries required**.

---

### Step 4: Package BOOT.BIN

```bash
# Add Vivado to PATH if needed
export PATH=$PATH:/tools/Xilinx/Vivado/2023.1/bin

./scripts/package_boot_bin.sh
```

**Output:** `BOOT.BIN` (~4–8 MB depending on bitstream)

---

### Step 5: Program QSPI Flash

#### Option A: Using program_flash (Vivado, JTAG)

```bash
./scripts/program_qspi.sh
```

#### Option B: Manually

```bash
program_flash \
  -f BOOT.BIN \
  -offset 0 \
  -flash_type qspi-x4-single \
  -cable type digilent
```

---

### Step 6: Set Boot Mode Jumper JP5

The Zybo Z7-10 has a boot mode jumper **JP5** (near the microSD slot):

```
JP5 Positions:
  ■■□  JTAG mode   (pins 1-2) ← factory default
  □■■  QSPI mode   (pins 2-3) ← set this for autonomous boot
```

After setting JP5 to QSPI (pins 2-3), power-cycle or press **SRST**.

---

### Step 7: Verify Boot via UART

Connect to the Zybo's USB-UART (usually `/dev/ttyUSB1`) at **115200 baud**:

```bash
screen /dev/ttyUSB1 115200
# or
minicom -D /dev/ttyUSB1 -b 115200
```

Expected output after power-on:

```

=======================================================
```

| LED | Signal      | Meaning |
|-----|-------------|---------|
| LD0 | `ready`     | ARM mailbox server running |
| LD1 | `irq_arm`   | ARM has a pending mailbox interrupt |
| LD2 | `irq_rv32`  | RV32 has pending data to read |
| LD3 | `mbr_valid` | First word of SD data buffer ≠ 0 |

## RV32 Test Program (instructions.hex)

The baked-in test program in `rv32i/instructions.hex`:

```assembly
# x5 = 0x43C00000  (mailbox base)
lui   x5, 0x43C00
addi  x5, x5, 0

# SD_ADDRESS = 100
addi  x6, zero, 100
sw    x6, 4(x5)        # MAILBOX[ADDRESS] = LBA 100

# CMD = READ (1)
addi  x6, zero, 1
sw    x6, 0(x5)        # MAILBOX[COMMAND] = 1

# REQ = 1 (trigger ARM)
addi  x6, zero, 1
sw    x6, 8(x5)        # MAILBOX[CONTROL] = 1

# Poll STATUS until DONE (2)
poll: lw   x7, 12(x5)
      addi  x8, zero, 2
      bne   x7, x8, poll

# Read first word of sector data
lw    x9, 0x20(x5)     # MAILBOX[DATA[0]]

# x9 now contains bytes 0-3 of SD sector 100
loop: jal zero, loop   # spin forever
```

## SD Card File System

The onboard SD card can contain any FAT32 file system (most SD cards come pre-formatted). The mailbox interface works at the **raw sector level** (512-byte LBA blocks) — it does **not** implement a file system. The ARM reads/writes exactly the sectors that the RV32 requests.

For file system access from the RV32:
- Implement a **FatFs** or **littlefs** library in the RV32 instruction ROM
- The RV32 issues raw sector reads, assembles sectors into FAT directory entries and file data
- This is the same way any embedded system (e.g., Arduino SD library) works

Common SD card layout:

| LBA Range | Contents |
|-----------|----------|
| 0 | MBR (Master Boot Record) |
| 1 – 2047 | Reserved / FAT32 VBR |
| 2048+ | FAT32 data clusters |

## Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| No UART output | JP5 in JTAG mode | Set JP5 to QSPI (pins 2-3) |
| "Invalid Mailbox signature" | Bitstream not loaded | Check bitstream in BOOT.BIN |
| "SD card not available" | No SD card inserted | Insert SD card in J1 |
| "ACMD41 timed out" | Power-up issue | Check SD card voltage / try another card |
| RV32 hangs in poll loop | ARM not running | Check UART for ARM startup message |
| `program_flash` fails | JTAG not connected | Check USB cable and JP5 is NOT in QSPI mode during programming |
